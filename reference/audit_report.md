## 0. 最後に答える5つの質問(先出し)

### Q1. ベーシックプランだけで、日×店舗×JANのPOSローデータ相当を全期間取得できるか？
**CONFIRMED(条件付き可能)**
「日別店別品名別ダウンロード」画面で日×店舗×JANの集計データ(Level 2、金額・数量・平均売価)を取得可能。ただし、
- 部門は契約上「70:化粧品」の1部門のみに限定される(他部門は選択肢自体が存在しない)
- 1回の実行は最大31日まで(実機確認済み)
- 小分類(カテゴリ)またはJANの指定が必須で、「全商品を無条件で一括」取得はできない(未指定で実行すると「JANコードもしくはカテゴリを第二階層以下に指定ください」というエラーになることを実機確認)
- データ蓄積期間は2021/5/16〜2026/8/24(実行日の2日前)

したがって「化粧品部門に限り、期間とカテゴリを分割しながら全期間分を積み上げ取得すること」は可能だが、契約対象外の部門を含む「完全な全社・全部門の日次POSローデータ相当」は取得不可。
根拠: screenshots/06_daily_store_sku_download.png, 06_dept_selected.png(部門が化粧品1つのみ), 06_execute_no_category.png(未指定エラー), samples/daily_store_sku_sample3.zip(実データ538行)

### Q2. 商品マスタ・店舗マスタを完全に取得できるか？
**CONFIRMED(店舗マスタは完全、商品マスタは契約組織範囲内で完全)**
- 店舗マスタ: ツルハグループ8事業会社・3,323店舗(閉店店舗含む)を無条件・一括で取得できた。事業会社・部門の制限は見られなかった。
- 商品マスタ: 176万8,833件を取得できたが、組織コードは全件「00538」(サン・スマイル)のみで、他7事業会社独自の商品マスタは同画面からは取得できない(店舗マスタと異なりスコープが組織単位)。
根拠: samples/store_master.zip, samples/product_master_prod.zip, screenshots/04_store_master_complete.png

### Q3. 匿名会員ID単位の購買明細を取得できるか？
**NOT AVAILABLE**
- 「データダウンロード」「拡張分析」配下のいずれのメニューにも「ローデータダウンロード」に相当する項目は存在しなかった(メニュー自体が非表示)。
- 実機で取得した全サンプルCSV(商品マスタ、店舗マスタ、日別店別品名別、プラノグラマー、在庫検索)のいずれにも会員ID・レシートIDに相当する列は存在しない。
- 唯一会員属性(性別・年代等)を扱えるメイン分析(マトリックス・クエリ・ブラウザ)も、出力は「人数」「リピート率」等の**集計値**であり、会員ID単位の明細行は出力されない。
- ヘルプサイト(https://jbtob.biz/help/)で「ローデータ」をフリーワード検索しても該当記事は0件だった。
根拠: download_catalog.csv の menu_no=16行、screenshots/02_data_download_dropdown.png、31_rawdata_search.png(検索結果0件)

### Q4. ベーシックのデータだけでSORANのID-POS分析をGCP上に完全再現できるか？
**NOT AVAILABLE(完全再現は不可)**
会員ID単位の生ログ(Level 1)が一切取得できないため、GCP側で新規に「任意の定義によるリピート率」「任意のコホート」「顧客セグメント別LTV」等を自由に再計算することはできない。一方で、SORAN側で既に計算済みの集計値(Level 3: 性年代別購入人数、リピート率等)をそのままGCPに蓄積すること自体は可能であり、「SORANが今表示している集計結果と同じ値をGCP上にも保持する」ことは実現できる。つまり「表示済みレポートの複製」は可能だが「新しい切り口でのID-POS再分析」は不可。
根拠: メイン分析の出力列に会員IDが含まれないこと(schema_catalog.csv)、ローデータダウンロード非搭載(Q3と同根拠)

### Q5. GCP基盤構築を目的とした場合、現契約のまま進めるべきか、プレミアム等のローデータオプションを契約すべきか？
**UNKNOWN(技術要件次第、商用判断はJBtoBへの確認が必要)**
- 目的が「売上・在庫のデータ基盤化(fact_pos, fact_inventory, dim_store, dim_product)」であれば、現行ベーシックプランの範囲で技術的には十分実現可能(ただし化粧品部門のみという制約は残る)。
- 目的に「顧客単位の分析(新規/継続、併買、LTV、コホート等)をGCP側で自由に行うこと」が含まれるなら、匿名会員ID付きの生ログ(ローデータダウンロード相当)を持つ上位プランへのアップグレードが技術的に必須。
- 契約変更・料金に関わるため、本調査だけでは断定できない。第10章「JBtoBに確認すべき質問」を参照。

- **商品マスタにおける他事業会社分の商品情報**: 商品マスタは組織コード00538のみを対象とし、他7社の独自商品情報は同画面からは取得できない(店舗マスタとは異なりスコープが狭い)。
- **住所・電話番号(店舗マスタ)**: フィールドは存在するが実データは全件空欄。

## 4. 最も重要なダウンロード経路(優先順位)

1. **日別店別品名別ダウンロード** ― fact_pos_daily_store_skuの直接ソース。化粧品部門限定だが最も基本的なPOSデータ。
2. **プラノグラマー連携** ― POS(月次)+店舗マスタ+商品マスタを1回でまとめて取得できる効率性が高い。ただしLZH展開に外部ツール(7-Zip等)が必要。
3. **在庫検索** ― fact_inventory_store_skuの直接ソース。直前在庫はほぼリアルタイムで取得可能。
4. **メイン分析(マトリックス・クエリ・ブラウザ)のCSV出力** ― Level3集計値を柔軟に取得できるが、次元選択がグリッドのセルクリック操作でありUI自動化の難易度が高い。
5. **商品マスタ・店舗マスタ(データダウンロード)** ― マスタ系。頻繁な更新は不要(週次/月次程度で十分)。

## 6. 初回バックフィル方法

実機で確認した制約(化粧品部門・31日/回・データ起点2021/5/16)を前提に概算する。

- データ起点: 2021/5/16、最新提供日: 2026/8/24 → 対象期間は約1,927日(約63.4ヶ月)
- 「日別店別品名別ダウンロード」は1回最大31日 → 単純計算で 1927 ÷ 31 ≒ **62回の実行が必要**(店舗グループ・カテゴリの分割方法によって回数は増減する)
- 店舗は事業会社単位で一括選択できることを確認したため(1871店を1グループとして追加成功)、店舗分割は基本的に不要と推定されるが、化粧品部門内のカテゴリ(大分類は711〜781等、実機で少なくとも8種類以上を確認)ごとに分けて実行する必要がある場合、実行回数はさらに増える可能性がある(未検証、UNKNOWN)。
- プラノグラマー連携を月次モードで代替に使う場合は、1回=1ヶ月分のため 63.4ヶ月 ≒ **64回の実行**で同等期間をカバーできる可能性がある(ただしPOS.CSVの粒度は月次集計であり日次粒度は失われる)。

## 7. 日次更新方法

- データ蓄積期間の実機確認により、**当日を基準に2日前(D-2)までしかデータが提供されない**ことを確認した(調査日2026/8/26に対し、最新提供日は2026/8/24)。
- したがって日次更新は「D-2の1日分を毎日取得」が基本方針となる。
- 遅延訂正(POSデータの後日修正)の可能性に備え、**直近7日間を毎回再取得して洗い替える方式**を推奨する(未検証の推測だが、一般的なPOS集計システムの実務慣行として妥当)。
- 在庫検索(直前在庫)は実行時点のスナップショットのため、日次で1回取得すればよい。

## 8. 自動化可能性

Windows上でのGUI自動化について、実際にPowerShell経由の座標クリック+スクリーンショット確認で操作した経験に基づく評価。

| 項目 | 内容 |
|---|---|
| GUI操作 | ボタン・カレンダー・ドロップダウンいずれも座標クリックで操作可能。ただしUI Automation(アクセシビリティツリー)による要素検出には対応しておらず、座標依存となる |
| ファイル保存 | 「実行」→サーバ側集計→ダウンロードURL表示→クリックでブラウザ(Edge)がダウンロード、という2段階プロセス。ファイル名はユーザー入力欄で指定可能な画面と、固定(prod.zip等)の画面が混在 |
| ダイアログ | 各実行後に「集計完了」ダイアログ→「閉じる」→「はい/いいえ」の確認、という2段階の後処理が必須 |
| 待機時間 | 集計時間は条件によって3〜15秒程度(店舗数・期間により変動)。プログレスバー表示があり、完了検知はポーリングで対応可能 |
| エラー処理 | カテゴリ/JAN未指定時のエラーダイアログ等、UI上のポップアップで通知される。テキスト検出による自動判定が必要 |
| セッション切れ | 今回の調査(約1時間強の連続操作)ではセッション切れは発生しなかった(UNKNOWN、長時間放置時の挙動は未検証) |
| 同時ログイン制限 | 未検証(UNKNOWN) |
| LZH展開 | Windows標準では非対応。7-Zip等の追加インストールが必要(本調査でwinget経由でインストール) |

**総合難易度**: **MEDIUM**。座標依存の自動化は解像度・DPI設定・ウィンドウ位置に敏感で壊れやすい(本調査でも画面解像度の誤検出=1280×800→実際は1920×1200、により何度か座標がずれた)。本番の定期自動化を組む場合は、固定の画面解像度・ウィンドウ位置を前提とした環境を用意し、失敗時のリトライ・アラートを組み込む設計が必須。
